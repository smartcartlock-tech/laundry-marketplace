# גיבוי ושחזור — מכבסה בקליק

## מה מגובה ואיך
- **גיבוי יומי אוטומטי מוצפן**: dump מלא של כל הטבלאות → JSON → AES-256-GCM → נשמר בטבלת `encrypted_backups` בבסיס עצמו (`src/backup-crypto.js`, רץ בתהליך השרת).
- **גיבוי ידני**: `POST /api/admin/backup/encrypted` (מנהל פלטפורמה).
- הצפנה: מפתח `BACKUP_KEY` ב-env של שירות הרנדר (נופל ל-`FIELD_ENC_KEY`). בלי המפתח אי אפשר לפתוח גיבוי.
- גיבוי לא-מוצפן (JSON גלוי) קיים ב-`GET /api/admin/export` — לצפייה בלבד, לא לגיבוי עיקרי.

## צפייה והורדה
- רשימה: `GET /api/admin/backups` (מנהל).
- הורדת קובץ `.wlb1` מוצפן: `GET /api/admin/backups/:id/download` (מנהל).
- בדיקת תקינות מול השרת: `POST /api/admin/backups/:id/verify` — מפענח ומחזיר רשימת טבלאות; שיבוש/מפתח שגוי → 422.

## שחזור מלא (תרחיש אסון)
1. להוריד את הגיבוי העדכני (ראו למעלה) או לשלוף את ה-payload ישירות מהטבלה.
2. להקים Postgres חדש (כל אינסטנס; אין תלות ברנדר).
3. להריץ אימות-שחזור מלא שגם משחזר בפועל לסכימה נפרדת וגם משווה ספירות:
   ```bash
   BACKUP_KEY=<from render env> TARGET_DATABASE_URL=postgres://user:pass@host:5432/newdb \
     node scripts/restore-verify.js --file laundry-backup-YYYY-MM-DD.wlb1
   ```
   יציאה `ok:true` = הגיבוי שוחרר במלואו לסכימת בדיקה (שנמחקת בסוף).
4. שחזור לייצור בפועל: להריץ את אותה לוגיקה (`src/restore.js`) מול בסיס הייצור לסכימה חדשה, לוודא תוצאות, ורק אז להחליף `PGSCHEMA` במשתני הסביבה של השירות ולעשות redeploy.

## גבולות ידועים
- הגיבוי מאוחסן באותו בסיס שהוא מגבה — אסון ברמת בסיס הנתונים כולו דורש הורדה תקופתית של קובץ `.wlb1` למקום אחר (פעולה ידנית של מנהל, עד שיוחלט על אחסון חיצוני).
- שחזור לייצור הוא פעולה ידנית מבוקרת — לא אוטומטית.
